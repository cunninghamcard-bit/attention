## 1. 核心愿景（Product North Star）

`attention` 的终极目标是成为**「编辑器界的浏览器」**，并解决一个核心痛点：**让 AI 带着人去读真实的原文，而不是让人自己在文件树里一个个点着读。**

传统 IDE（VS Code、Zed）假定「人自己知道要去哪个目录、点开哪个文件、跳到哪一行」；而现有的 AI 对话工具又往往把代码和文档嚼碎成脱离上下文的聊天摘要，失去了真实原文的准确性与上下文结构。

`attention` 走第三条路：

1. **只看真实的原文（Grounded in Real Originals）**：主画布永远呈现真实的代码文件、真实的 Markdown 原文、真实的网页和真实的终端实验输出，不做虚假的「生成式课程」或脱离原文的二手总结。
2. **AI 做苦力，人做检阅与决策**：搜索、网页检索、跨文件读代码调研、跑终端实验验证，全部由外部 AI Agent 完成；AI 的产出是一条条直接锚定到真实原文具体位置（`path` + `line..to`）的导读流。
3. **像浏览器一样轻量，像信息流一样顺滑**：从底层单文件读写，到顶层「一个 Tab 就是一个项目/探索空间」，再到类似 Slack / 卡片流的「AI 推送 + 左右滑筛选（Triage）」，按阶段渐进演化。

## 2. 产品线三阶段演进

为了避免一开始陷入过度复杂的交互设计，产品线明确划分为三个阶段推进：**先把阶段一（简单、干净、好用的原生编辑器）做扎实**，再逐步长出阶段二和阶段三的浏览器化与 AI 导读交互。

### 阶段一（V1 · 当前重心）：简单、好用的原生编辑器与阅读底座

在叠加酷炫的 AI 交互之前，`attention` 首先必须是一个体验顺滑、架构干净的轻量级原生编辑器：

- **可编辑与无感自动保存（Obsidian 模式）**
  - 去掉早期 spike 阶段的 `ReadOnly: true` 限制，源码（`text`）与笔记（`markdown` 源码态）均可直接编辑。
  - 采用 **Obsidian 式无感自动保存**：停止输入后防抖（约 1~2 秒）自动通过 `fs.Write` 写回磁盘，同时支持 `Ctrl+S` / `Cmd+S` 立即落盘；界面无需维护复杂的未保存圆点状态，并在写入侧抑制 `fsnotify` 触发自身二次重读。
- **内存级增量 `MetadataCache`**
  - 保留并固化现有的内存缓存抽象（`internal/mdmeta` + `plugins/index`）：在内存中实时维护标题（Headings）、行号定位、双链解析（`resolvedLinks` / `unresolvedLinks`）、反链（Backlinks）、标签（Tags）、Frontmatter 属性以及网页 URL 跨类型反链。
  - 不引入沉重的本地 SQLite 索引库，也不保留未落地的泛化 `extractors` 进程间注册表。
- **统一的原生外观系统**
  - 按 [docs/appearance.md](appearance.md) 落地仿 Zed 的简洁外观配置（亮暗模式、字体家族、字号、行高），统一作用于 UI 外壳、代码编辑器、Markdown 视图与内置终端。
- **干净的进程内插件接线**
  - 推动上游 `go/rutis` 支持同进程（`s.Local() == true`）直接传递 Go 接口与闭包，逐步消除 `native/` 下为绕过序列化而建的 10 个 `*api` 全局单例包。
  - 外壳底座（`Shell` + `Layout` + `Workspace` + `Shortcuts` + `Settings`）内聚，业务插件统一通过 4 个标准扩展点（`TabType`、`Slot`、`Command`、`Resource`）接入。

### 阶段二（V2）：「编辑器界的浏览器」——文件 Tab 携带所属 Project 上下文

传统编辑器（VS Code、Zed）之所以笨重，是因为规定「一个窗口死绑一个 Project（文件夹）」——想看另一个项目的代码就必须新开窗口或切换整个工作区。而如果强行规定「新建一个 Tab = 新建一个 Project」，又违背了「打开一个文件生成一个 Tab」的自然直觉。

因此，阶段二将关系反过来设计：**以文件 Tab 为自然单元，Project 作为文件 Tab 携带的属性与旁侧列（Column）**：

- **打开文件即生成 Tab，每个文件 Tab 自带所属 Project 信息**
  - 同一个窗口的标签栏里，可以自然地混开不同 Project 的文件 Tab（例如 Tab 1 是 `attention` 的源码，Tab 2 是 `rutis` 的源码，Tab 3 是网页）。
  - **新建 Tab（New Tab Page）**：就像浏览器的起始页，展示常用 Project、最近打开的文件、全局搜索框或 AI 入口；从中点选任意项目的文件，该 Tab 即成为那个文件的 Tab。已实现为起始页，见 [RFC 0003](rfc/0003-arc-layout.md)。
- **文件夹作为一列（侧边栏），随当前文件 Tab 动态切换与展开**
  - 旁侧的文件夹列不死绑整个窗口，而是自动跟随当前激活的文件 Tab 切换所属 Project。曾考虑以下三种候选形态，**已定为形态 A**（[RFC 0003](rfc/0003-arc-layout.md)）：
    1. **形态 A（自动跟随的侧边列 / Context Sidebar）**：侧边列始终展示当前文件 Tab 所属 Project 的目录树，默认只展开当前文件所在的文件夹层级（同级兄弟文件一目了然），其余目录折叠。
    2. **形态 B（面包屑抽屉列 / Breadcrumb Column）**：默认只看文件正文与顶部路径栏 `[Project] / dir / file.go`；点击路径上的 Project 或文件夹时，在旁侧展开一列显示该层级的其他文件。
    3. **形态 C（精简上下文列 / Related Files Column）**：默认不展开庞大的全量目录树，旁侧列直接聚合展示「所属 Project 入口 + 同级目录文件 + 引用/反链关联文件 + AI 推荐关联文件」，需要时再展开完整文件夹。
- **AI 可编程的视图编排**
  - 打开文件、跨项目调取关联文件、分屏对比、打开网页或终端，不再只能靠人手点。AI 可以通过 CLI / 服务接口直接替用户打开对应的文件 Tab（自动带上其所属 Project 上下文），把准备好的一组视图直接摆在用户面前。
- **统一地址与导航栏（Omnibox）**
  - 融合本地资源地址（`attention-resource://...`）、网页 URL（`https://...`）、行号区间（`line=..to=..`）与命令面板，提供浏览器式的直达体验。已实现合并模式（标签页、文件、网页、命令），见 [RFC 0003](rfc/0003-arc-layout.md)。

### 阶段三（V3）：AI 主导的导读流与左右滑分拣（AI-Guided Reading & Swipe Triage）

当编辑器底座和浏览器式多项目容器就绪后，进入核心产品形态——**让 AI 带着人读东西**：

- **不内置重型 Subagent，直接赋能外部 Agent**
  - `attention` 自身不重复造 Agent 推理循环或内置复杂的 subagent 编排，而是把编辑器能力通过 CLI 与 `rutis` 彻底暴露给外部 Agent。
  - 外部 Agent 可以通过 4 种核心手段替用户寻找答案并产出证据：
    1. **本地搜索**：调用全文搜索与 `MetadataCache`（大纲、反链、标签、属性）快速缩小范围；
    2. **网页搜索与抓取**：通过内置 `web` / `web:read` 检索外部文档、Issue、博客并抽取干净正文；
    3. **代码深度调研**：顺着目录结构与调用上下文阅读多处源码；
    4. **动手做实验**：在内置终端（`terminal`）或沙箱中跑测试、执行脚本、复现问题，拿到真实运行输出。
- **推送式阅读流（Slack 式信息流 + 原文联动）**
  - AI 在调研或实验过程中，不再只吐出一段长篇大论的聊天回复，而是向 `attention` 推送一张张结构化的**导读卡片（Reading Card）**：包含「一句话结论 / 为什么看这里」+ **精确的原文锚点（文件/网页地址 + `line..to` 行号区间 / 终端输出片段）**。
  - 选中或切到某张卡片时，主编辑器画布立刻打开对应的**真实源文件 / 原网页**，精准滚动并高亮 `line..to` 关键行段。
- **左右滑交互（Swipe Triage）**
  - 面对 AI 推送过来的一组候选代码位置、调研发现或改动建议，用户不需要在文件树里迷路，只需通过极低心智负担的交互（左滑 / 右滑，或快捷键 `J/K`、`H/L`）快速分拣：
    - **右滑（确认 / 保留 / 深入）**：标记为有效线索、钉住（Pin）到当前阅读路径，或让 AI 顺着这段代码继续往下深挖；
    - **左滑（跳过 / 忽略）**：直接略过噪音，瞬间切到下一张导读卡片对应的真实原文位置。

## 3. 待深入讨论的产品设计议题

随着阶段一底座收尾，后续可以围绕以下几个产品线细节继续展开讨论：

1. **文件 Tab 旁侧「文件夹列」的展开方式（形态 A / B / C 的取舍）**：已定为形态 A，见 [RFC 0003](rfc/0003-arc-layout.md)。
2. **导读卡片（Reading Card / Trail）的最小数据协议**：
   - CLI 需要新增怎样的命令（例如 `attention push` 或 `attention trail:add path=... line=... to=... note="..."`），才能让任何外部 AI 工具用一行命令就把一段原文高亮卡片推送进编辑器？
3. **阅读时的随手批注与反馈闭环**：
   - 当用户在「右滑确认」或阅读某段真实源码时，如何以最轻量的方式留下一句批注或追问，并直接作为上下文回传给正在工作的 AI？
