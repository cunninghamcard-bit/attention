## lifecycle：LSP lifecycle and capability negotiation

**问题**：initialize/initialized/shutdown/exit; ClientCapabilities vs ServerCapabilities for the read-side methods; workspaceFolders; positionEncoding (utf-8/utf-16/utf-32) negotiation and which servers support utf-8; what a minimal read-only client must advertise.

**摘要**：LSP 生命周期与能力协商的结论：initialize 必须是客户端的第一个请求，InitializeResult 之前客户端不得发其他请求或通知；initialized 只能发一次；shutdown 之后只允许 exit，exit 的退出码取决于是否先收到 shutdown。编码协商：客户端在 general.positionEncodings 声明可接受编码（未声明则默认 utf-16），服务端在 ServerCapabilities.positionEncoding 选定一个（未声明则 utf-16）。3.18 与 3.19 的 initialize.md 内容相同。已核对的服务端中，rust-analyzer 与 ruff/ty 会协商 utf-8；pyrefly、rust-glancer 硬编码 utf-16；zed 只声明 utf-16。对 Acard（Go 客户端，字符串为 UTF-8 字节）而言，最小只读客户端应首选 utf-8 并保留 utf-16 兜底。

## textsync：Text document synchronization for a reading client

**问题**：didOpen/didChange/didClose/didSave; full vs incremental sync; must a read-only viewer still didOpen a file to query it; do servers answer requests for files never opened; versioning.

**摘要**：LSP 文本同步（didOpen/didChange/didClose/didSave）规范与三个实现的行为已核对。规范要点：didOpen 之后内容由客户端托管，服务器不得再通过 URI 读取该文档内容；open/close 必须成对且同一文档最多一次 open；服务器回答请求的能力与文档是否 open 无关。同步是客户端的强制义务（客户端不能不支持 didOpen/didChange/didClose），服务器必须三者全实现或全不实现，只有文档对客户端只读时才有意义选择不同步。版本号在每次变更（含 undo/redo）后递增，不要求连续。对一个只读阅读器而言：规范允许不发 didOpen 直接按 URI 查询（服务器应从磁盘/工作区读取），但按规范客户端仍须支持这三个通知；rust-analyzer 与 ty 都用 Incremental 同步，且 rust-analyzer 对未 open 文档收到 didChange 只记错误并忽略。

1. [fact/high] didOpen 通知：客户端通知服务器文档已打开，文档内容此后由客户端管理，服务器不得再通过该 URI 读取文档内容；open 与 close 必须平衡，同一文档 open 次数上限为 1；服务器处理请求的能力独立于文档是否 open。

## diag：Diagnostics: push vs pull

**问题**：textDocument/publishDiagnostics vs textDocument/diagnostic and workspace/diagnostic (pull, 3.17), relatedDocuments, resultId, DiagnosticTag (Unnecessary/Deprecated), relatedInformation; which of rust-analyzer/ty/pyright/pyrefly use push or pull.

## workspace：Workspace, configuration and file watching

**问题**：workspace/didChangeWatchedFiles and client/registerCapability dynamic registration with glob patterns; workspace/configuration pull vs didChangeConfiguration push; workspace/didChangeWorkspaceFolders; which server-to-client requests a client MUST answer or the server stalls.

**摘要**：LSP 3.18 规范中，workspace 相关能力分三类：(1) 文件监听走动态注册：服务端用 client/registerCapability 注册 workspace/didChangeWatchedFiles，registerOptions 为 watchers 列表，每项是 GlobPattern（字符串或 RelativePattern{baseUri,pattern}，3.17 起）加可选 kind 位掩码（Create=1/Change=2/Delete=4，默认 7），客户端通过 workspace.didChangeWatchedFiles.dynamicRegistration 与 relativePatternSupport 声明能力；事件类型为 Created=1/Changed=2/Deleted=3。(2) 配置是拉模型：服务端发 workspace/configuration 请求（items 为 scopeUri+section），返回数组与 items 一一对应，无法提供时该位置填 null；规范明确这取代了旧的 didChangeConfiguration 推模型，服务端若需感知变化应注册一个空的 didChangeConfiguration。(3) workspace/didChangeWorkspaceFolders 可经 server capability workspace.workspaceFolders.changeNotifications 或动态注册（method 为该通知名）获得。关于阻塞：规范规定每个已处理的请求必须回送响应，但并未逐条列出哪些服务端请求会使服务端停滞；14 个 serverToClient 请求中，registerCapability/configuration/workspaceFolders/applyEdit/showMessageRequest 等都需要响应，规范对未识别的非 $/ 请求没有强制 MethodNotFound 要求（只对 $/ 前缀要求）。实现上，helix 对未知方法回 MethodNotFound，但对非文件类的 registerCapability 注册直接回 success(null) 以绕过 vscode-languageserver-node 系服务器的致命错误；rust-analyzer 与 zed 都在 registerCapability 中使用 RelativePattern 或在客户端不支持时退回绝对路径字符串。
