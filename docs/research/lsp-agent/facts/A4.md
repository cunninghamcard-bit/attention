## zed-lsp：Zed: LSP transport and advertised capabilities

**问题**：How Zed spawns a server process and frames JSON-RPC (crates/lsp/src/lsp.rs), which ClientCapabilities it advertises for read features, request timeout handling, stderr/log capture.

**摘要**：Zed 的 LSP 客户端（crates/lsp）以 std 子进程方式启动服务器：stdin/stdout/stderr 全部 piped 并 kill_on_drop，stdout 按 Content-Length 帧解析 JSON-RPC，请求用 AtomicI32 自增 id + HashMap 回调表，超时由 select! 计时器实现，默认 120 秒，0 表示不超时。stderr 只在启动阶段按行捕获，启动失败时作为 "-- stderr --" 附在错误状态里。客户端广告的读功能能力很完整（definition 的 linkSupport、hover 仅 Markdown、semanticTokens full delta 与 RELATIVE 格式、hierarchical documentSymbol、callHierarchy、pull diagnostics 按开关），但 positionEncodings 只声明 UTF-16。下面的数字和路径均已在本地源码中核实。

1. [fact/high] 启动服务器时 Command 设置 current_dir 为 root（若 root 是文件则取父目录），args/env 来自 binary，stdin/stdout/stderr 均 Stdio::piped()，并 kill_on_drop(true)；启动前用 log::info 记录 binary path、工作目录与参数。  
   来源：~/Projects/lsp-ref/zed/crates/lsp/src/lsp.rs:515-560（LanguageServer::new，命令构造约 L540-548）

   来源：~/Projects/lsp-ref/zed/crates/lsp/src/input_handler.rs:17（HEADER_DELIMITER）、input_handler.rs:27-44（read_headers）、input_handler.rs:83-130（handler 主循环）
3. [fact/high] 入站消息队列容量为 INCOMING_MESSAGE_QUEUE_CAPACITY = 128；队列满时读取端停止读取 stdout，借 OS 管道对服务器施加背压，而不是无限缓存；对应测试断言缓冲消息数不超过 130。  
   来源：~/Projects/lsp-ref/zed/crates/lsp/src/input_handler.rs:24-30（常量及注释）、input_handler.rs:~138-170（test_backpressure_when_messages_are_not_consumed）

5. [fact/medium] 请求 id 为 AtomicI32 自增的 RequestId::Int；回调保存在 Arc<Mutex<Option<HashMap<RequestId, ResponseHandler>>>> 中，服务器关闭时 take() 置空并让 pending 请求得到 ConnectionReset。

## zed-store：Zed: lsp_store, server instances per worktree, restart, status UI

**问题**：How LspStore maps worktrees/roots to server instances, multiple servers per language, restart/stop, crash handling, server status and log viewer UI (language_tools crate).

**摘要**：Zed 的客户端 LSP 生命周期分三层：ManifestTree 找每个语言的子项目根（manifest 所在目录，缺省为 worktree 根）；LanguageServerTree 按 worktree → 根路径 → server name 缓存节点，并按 settings 决定该语言启用哪些 adapter（允许同一语言多个 server）；LocalLspStore 用 LanguageServerSeed（worktree、name、binary/initialization_options 设置、toolchain）去重进程，不同子根若 seed 相同则共享同一个进程（project_roots 记录多个根）。停止/重启以 server id 或 name 为选择器，重启 = 先 stop 再对已注册 buffer 重新 register。崩溃后本地没有找到自动重启逻辑：进程退出只是 IO 任务结束，条目仍停留在 Running 状态，直到用户手动 Restart。UI 侧 language_tools/lsp_button.rs 提供状态灯（Ok/Warning/Error、Starting/Stopping/Failed）、Restart/Stop/View Logs 子菜单；日志视图在 log_store 中以每 server 2000 条的环形缓冲保存。注意：BinaryStatus、ServerHealth 的定义文件在本地浅克隆中未找到，相关结论只基于使用侧代码。

**摘要**：Helix 对 LSP 读取类结果的呈现逻辑很统一：goto definition/declaration/type definition/implementation/references 都先并发收集所有服务器的结果并拍平成一个 Vec<Location>，只有 0 个（报错）或 1 个（直接跳转）时不弹出 UI，多个结果则统一进入带预览的 Picker（列为 相对路径:行号）。hover 按服务器聚合成 auto_close 的弹出框，多服务器时用 alt-p/alt-n 切换。document/workspace symbol 与 diagnostics 都是 Picker，诊断在 gutter 中以一个 ● 按最高严重级别着色。jumplist 是每个 View 持有的、容量 30 的 VecDeque，Ctrl-o/Ctrl-i 前后移动，跳转前由 push_jump 记录当前 (DocumentId, Selection)。以上结论均基于本地 helix 仓库 ba40e54（2026-09-29）的源码，未使用网络来源。

## encoding：Position encoding and text sync pitfalls

**问题**：UTF-16 vs UTF-8 positions, CRLF, incremental change application; how Helix (ropey) and Zed convert; which servers accept utf-8 (rust-analyzer, ty, pyright?); implications for a Go client storing text as UTF-8 bytes.

**摘要**：LSP 位置编码以 UTF-16 为强制默认值，3.17 起允许 client 通过 general.positionEncodings 协商 utf-8 / utf-32。实际表现分三类：ty、rust-analyzer、helix 三者都会协商 UTF-8（ty 最偏好 UTF-8，rust-analyzer 偏好 UTF-8 其次 UTF-32，否则回落 UTF-16）；Zed 只宣告 utf-16；pyrefly 硬编码 utf-16。Helix 用 ropey 在 char、UTF-8 字节、UTF-16 code unit 之间换算，并按服务端返回的 positionEncoding 选择分支；CRLF 方面，LSP 规定 \n、\r\n、\r 都是行终止符，position 与行终止符无关，helix 自己承认在 unicode-linebreak 下存在不合规的 FIXME。Zed 发增量变更前先把文本 LF 归一化，行尾风格变化时整文档重同步。对 Go 客户端（文本存 UTF-8 字节）的含义：必须按服务端协商结果做 UTF-16 列换算（Go 标准库 unicode/utf16 可用），默认只宣告 utf-16 最安全，宣告 utf-8 则可省换算但要保证服务端确实接受。
