## dim-overview：dim: architecture overview

**问题**：What dim is, its components (runtime, App Server, clients, model host), the Timeline concept, sessions and branches, from the architecture docs. Skip ACP.

**摘要**：dim（arcships/dim，Rust 实现 alpha）的定位是"能随所处环境成长的通用智能体"范式。核心是事件驱动的 Timeline：每个分支一条总线，只有 Timeline 提交分配序号，运行时完全由插件（rutis 0.19.3 插件）构成。架构分层为：终端 CLI/Web 等客户端通过协议 v3 的本地 NDJSON RPC 连接 App Server 守护进程；App Server 持有 Agent v4 执行、审批、模型/Provider 选择与原生存储；模型宿主（dim-agent-aimux）提供 OpenAI/Anthropic/Gemini 等协议适配；可选的托管 Provider 是 account 构建的 Rust 进程插件。对象模型为 Agent > Session > Branch，Session 是"我"（身份、交互面、能力、工作区），分支是同一主体的一条行为线；父子分支通过切点继承历史，共享事实而不共享上下文。Timeline 是事实的唯一来源，持久化是其属性而非本质。ACP 相关内容按边界略过。

1. [fact/high] dim 自称为“general-purpose agents that grow into the environments they inhabit”的范式；运行时完全由插件构成，插件可用 Rust、TypeScript 或 Python 编写。  
   来源：~/Projects/dim-ref/README.md:7,13
2. [fact/high] 架构分层：Terminal/npm launcher → Rust dimcode → 经认证的本地 NDJSON RPC → Rust dim-app-server，其下分为 Agent v4（Timeline、Dispatcher、Capabilities、Storage）与 Provider host（API-key/原生模型连接，可选托管 provider 插件）。  
   来源：~/Projects/dim-ref/docs/architecture/README.md（架构 ASCII 图，文件开头段）
3. [fact/high] README 说明 Rust harness 可作为库嵌入；App Server 在其上提供持久化、工作区工具并向客户端暴露 sessions；终端 CLI 只是其中一个客户端。  
   来源：~/Projects/dim-ref/README.md（“Clients, tools and model protocols”一节，“The Rust harness can be embedded as a library”）
4. [fact/high] App Server 与 CLI 之间走私有 Unix socket（NDJSON）或 Windows named pipe；WebSocket 端点在 product/configured 档只允许 hello 与 ping，仅显式 mock 档允许 WebSocket 执行。  
   来源：~/Projects/dim-ref/crates/dim-app-server/README.md（开头段）
5. [fact/high] CLI 是客户端而非另一个执行引擎：CLI 拥有命令行输入、scrollback 输出、审批与提问；App Server 拥有模型执行、工具、会话状态与持久化。  
   来源：~/Projects/dim-ref/crates/dim-cli/README.md（开头段）；docs/architecture/README.md “The CLI is a client, not another agent execution engine.”
6. [fact/high] 客户端分为 Native CLI（dimcode，已实现）、Web workspace（Vue 3，phase 1 已实现，loopback 入口）、Desktop（独立仓库，不在本仓库）、ACP（子集已实现，未发布）、Remote devices（P3 草案，未实现）；均为协议 v3 客户端，同一守护进程一个执行者多个查看者。  
   来源：~/Projects/dim-ref/docs/design/clients.md §1 表格与 mermaid 图（“one daemon per product home, one executor with many viewers”）
7. [fact/high] 模型协议由 aimux 提供，支持 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Gemini GenerateContent 及兼容 chat 端点；aimux 为 vendored 代码（MIT），固定版本见 vendor/aimux/SOURCE.md。  
   来源：~/Projects/dim-ref/crates/dim-agent-aimux/README.md（开头段）；~/Projects/dim-ref/README.md 表格“Model providers”行
8. [fact/high] crate 依赖约束：dim-agent-types 不依赖 Tokio、rutis、HTTP 或 capabilities；dim-agent-runtime 不引用默认 capabilities 或 App Server；dim-app-server 组合 runtime 与 capabilities 且不引用 CLI；dimcode 只做组合，不被依赖。  
   来源：~/Projects/dim-ref/docs/architecture/README.md “## Crates” 表格（约 46–60 行）
9. [fact/high] 对象模型：Agent 持有配置、Session 注册表与其插件（不跑模型循环，一份配置可创建多个 Session）；Session 持有工作区、审批、TimelineTree 与 Session 级 capability，Session 之间不共享可变业务状态。  
   来源：~/Projects/dim-ref/docs/architecture/README.md “## Objects” 表格（约第 61–70 行）
10. [fact/high] Timeline 是“每个分支的时间总线”：事件写上总线，总线分配序号，按序驱动订阅者；持久化是总线的性质而非本质；已发布事件不再变更，是唯一的历史事实。  
   来源：~/Projects/dim-ref/docs/architecture/rust-agent/time-bus.md §0 开头段与 §1；docs/architecture/README.md “## Objects” 中 Timeline 行
11. [fact/high] Timeline 事件排序规则：只有 Timeline 提交分配 sequence；先后只看序号，不看执行快慢或完成先后；每个分支有一个串行 Dispatcher；handler 中的追加进入尾部、稍后分发而非递归。  
   来源：~/Projects/dim-ref/docs/architecture/README.md “## Event conventions”（约第 75–82 行）；time-bus.md §1
12. [fact/high] 存储结构：Timeline 持有热窗口与发布水位，写入经写入任务按轮提交并 fsync 后才推进发布水位；Dispatcher 只消费热窗口中已发布的事件；冷读取走 TimelineStore。进程 SQLite 服务（SessionStorePlugin）实现 TimelineStore，内存实现 MemoryTimelineStore 供独立 AgentBuilder/测试使用。  
   来源：~/Projects/dim-ref/docs/architecture/rust-agent/timeline-storage.md §1 结构图与模块表（约第 5–31 行）
13. [fact/high] 分支（Branch）是同一 Session 内同一主体的一条行为线；子分支继承父分支切点之前的历史，此后各自折叠自己的事件；分支之间共享历史事实而不共享上下文，各自组装上下文并各自压缩（compaction）。  
   来源：~/Projects/dim-ref/docs/design/timeline-branches.md §1（第 5–15 行附近）；docs/architecture/rust-agent/principles.md 第 29 行
14. [fact/high] 分支与 Collaboration member、fork 的区分：branch 与 Session 同身份同能力同 workspace；member 是另一个 Session（另一个 profile）；fork 是从 main 复制的独立 Session。需要不同身份或能力时应新建 Session 而非分支。  
   来源：~/Projects/dim-ref/docs/design/timeline-branches.md §2 对比表
15. [fact/high] 分支间唯一的通信与读取关系是父子关系：父子互相写输入（input/message），子分支读取其切出的那条线；兄弟分支不直接通信。main 是根线，agent 的 branch 工具只能从 main 开线，工具线为叶子不能再开线。  
   来源：~/Projects/dim-ref/docs/design/timeline-branches.md §4 “Kinship”、“The agent's tool” 条目；docs/architecture/rust-agent/principles.md 第 29 行
16. [fact/high] 消息 mode：append（默认）随接收方下一次模型请求生效，不启动 turn、不唤醒 wait；steer 在接收方当前 turn 的下一步进入，空闲时则启动 turn 并唤醒 wait。  
   来源：~/Projects/dim-ref/docs/design/timeline-branches.md §6 表格
17. [fact/high] Timeline 与 Session 的关系：Session 创建时由 SessionScope 以 Session 名字提供 timelineStore，各分支的 Timeline 从中读写；Session 的 TimelineTree 管理分支目录、创建、结束与关闭结算。  
   来源：~/Projects/dim-ref/docs/architecture/rust-agent/timeline-storage.md 第 31 行；principles.md §表 “Session 管理自己的分支”
18. [fact/high] 模型只看到已采纳的输入与工具结果；事件不直接进入模型上下文；需要进入上下文的能力必须写入采纳输入或在工具结果中返回。  
   来源：~/Projects/dim-ref/docs/adr/001-harness-foundation.md “Model-context boundary”；docs/design/overview.md §1 “Model context”行
19. [fact/high] 事件信封共享：运行时机制事实、公共能力协议事件与领域事件使用同一信封与持久化路径；Rust 的 EventKind 枚举只是核心定义事件的类型化视图，未定义的事件以不透明数据承载；Timeline 写入检查仅限信封结构与保留域，不校验 payload。  
   来源：~/Projects/dim-ref/docs/adr/001-harness-foundation.md “Events and ownership (issue #2)”
20. [fact/high] rutis 版本固定为 0.19.3（Cargo workspace 依赖 rutis、rutis-loader、rutis-bridge 均为 0.19.3）；Rust 工具链 1.98.1。  
   来源：~/Projects/dim-ref/Cargo.toml:14-16；~/Projects/dim-ref/README.md 徽章行（Rust 1.98.1）
21. [fact/high] 进程级 rutis root 唯一；Session 与分支是按实例键控的作用域子树；Timeline 持有持久状态，TimelineContext 持有运行时内存状态；仅 I/O 资源（进程、连接、流）不可重建，重载或重启时结算为终态。

## dim-rutis：dim: how it uses rutis (ADR 006)

**问题**：Plugins as loader rows, parts registered per session/branch, services by type and name, cross-language runtimes, event bus; what dim adds and refuses to add; the host connection-row form (appendix A.4).

**摘要**：dim 把 rutis 当作插件机制的唯一所有者（ADR 006 D2），自己只在其上定义领域层：实例树（agent/session/branch）、Timeline、服务目录与公开总线事件。核心约定有三条：一个插件 = loader 中的一行（row）；Session/branch 的 part 不是配置行，而是插件在运行时向 part registry 注册 generator，每个实例挂载一份；服务是 camelCase 名字且唯一属于一个 group（process/session/branch），按实例就近解析、不回退。跨语言运行时（Node 的 session-node、Python 的 py）是 dim-app-server 中的一条连接行 RuntimeConnection，由它用 rutis_bridge::runtime::Launcher 启动子进程、等待 30 秒问候、以 RuntimeStatus 暴露 starting/ready/down 状态。事件总线是 rutis 0.15.1 起的单一平总线，payload 必须是 serde，Dim 明确拒绝再加 plugin trait、manifest、第二套服务目录、第二条总线或逐语言适配层。dim 与 rutis 均锁定在 0.19.3。

1. [fact/high] Dim 的 Cargo.toml 固定依赖 rutis 0.19.3（rutis、rutis-loader、rutis-bridge 三者同版本）。  
   来源：dim-ref/Cargo.toml:14-16 (dim-ref 842ceb5 2026-11-08)
2. [fact/high] 本地 rutis 克隆的三个 crate（rutis、rutis-loader、rutis-bridge）版本均为 0.19.3，与 Dim 依赖一致。  
   来源：rutis/crates/rutis/Cargo.toml:5、rutis/crates/rutis-bridge/Cargo.toml:6、rutis/crates/rutis-loader/Cargo.toml:5 (rutis 4dc5cac1 2026-11-01)
3. [fact/high] 一个 rutis 插件在进程中对应一个 loader row；Session 与 branch 的 part 不是 row，由插件在 apply 中向 part registry 注册 generator，再由每个实例挂载。  
   来源：dim-ref/docs/design/rutis-usage.md §2 开头；dim-ref/docs/adr/006-plugin-contract.md D3（ADR 2026-10-24 接受，D3 于 2026-10-25 修订）
4. [fact/high] loader row 的字段为 id、name、config、inject、isolate、disabled；name 有三种形式：内置名、路径或 npm 包名（Node 运行时），以及 `<runtime row>:<module>`（如 py:<module>）。  
   来源：dim-ref/docs/design/rutis-usage.md §2 行字段表
5. [fact/high] part registry 是一个进程级服务（以进程名 partRegistry 提供给插件）；注册是调用者的 effect，随插件 generation 存活，卸载时撤销。  
   来源：dim-ref/docs/design/rutis-usage.md §2 'Registering a part'；ADR 006 D3
6. [fact/high] 实例挂载时分两个 mounter：required mounter 承载装配 profile 要求的 part，创建实例时等待其 Active 后才发布；optional mounter 承载其余 part，发布前让其沉降，失败或 Pending 的 optional part 只影响自身。  
   来源：dim-ref/docs/design/rutis-usage.md §2 'Mounting'；ADR 006 D3 'Publication'
7. [fact/high] 跨语言插件注册的是 definePlugin 产生的 definition；每个实例通过 Definition::at 挂一份副本，卸载时通过 Definition::ended 结束；definition 不能对某实例返回“无”。  
   来源：rutis/crates/rutis/src/definition.rs:144（at）、:176（ended）；dim-ref/docs/design/rutis-usage.md §2 'What a plugin registers'
8. [fact/high] 外部语言的 row 在启动前必须声明其 part 会提供的名字（instanceNames，附带 group），App Server 在运行时启动前完成注册；否则 rutis 会把该名字当作整个进程范围的单一 provider，第二个实例的副本会因重复 provider 失败。  
   来源：dim-ref/docs/design/rutis-usage.md §2 'What a foreign row still declares' 与 §3.5 'Provided names'
9. [fact/high] 服务名为 camelCase，且唯一属于一个 group（process、session 或 branch）；名字按实例就近解析，不回退到其他 group；同一实例内同名只能有一个 provider。  
   来源：dim-ref/docs/design/rutis-usage.md §3.1；ADR 006 D4
10. [fact/high] 服务跨语言的条件是每个方法的参数与返回值都是 serde 数据；含借用值、channel、handle 或在 commit lock 内同步回调的方法只能保留在 Rust 内，目录中标记为 Rust-only，不提供手写适配层。  
   来源：dim-ref/docs/design/rutis-usage.md §3.3；ADR 006 D4 'Rust-only services stay in the catalog'
11. [fact/high] 跨语言服务用 #[rutis::service] 在 Rust 类型上声明名字；目录由 `xtask graph` 从真实装配生成，`xtask check` 在目录过期时失败。  
   来源：dim-ref/docs/design/rutis-usage.md §3.4 与 R4
12. [fact/medium] rutis 0.17 删除了 build script 的服务列表（Exports::service_in），改用 #[rutis::service] 标记。  
   来源：dim-ref/docs/design/rutis-usage.md §3.4 'Today'
13. [fact/high] 本地运行时是 App Server 中的一条连接行（ForeignRuntime / RuntimeConnection）：用 rutis_bridge::runtime::Launcher 启动进程（--id <row>），stderr 逐行写入日志，并等待问候后挂载 Session::new(channel)。  
   来源：dim-ref/crates/dim-app-server/src/session_typescript.rs:16、:144-148、:343-360、:494-529 (dim-ref 842ceb5 2026-11-08)
14. [fact/high] 等待运行时问候的超时为 30 秒（GREETING = Duration::from_secs(30)）。  
   来源：dim-ref/crates/dim-app-server/src/session_typescript.rs:340
15. [fact/medium] Node 运行时启动命令为 `node --import tsx <packages>/src/runner.mjs`，Python 运行时为 `python -m rutis`；文档要求 Python 3.12 或更高。  
   来源：dim-ref/crates/dim-app-server/src/session_typescript.rs（launch command 注释，约 :365-400）；dim-ref/docs/design/rutis-usage.md 附录 B
16. [fact/high] 运行时状态以 RuntimeStatus（starting、ready、down 加原因）存放在 RuntimeStatus::key(row) 处；进程启动失败或退出时 row 仍保持 Active，使状态可读。  
   来源：dim-ref/crates/dim-app-server/src/session_typescript.rs:430-457、:475-494；dim-ref/docs/design/rutis-usage.md 附录 A.4
17. [fact/high] 两种运行时的 row 由同一个 SessionResolver::npm(catalog, "session-node") 解析：py:<module> 交给 py session，其余外部名交给 session-node；Dim 的 SnapshotResolver 只包裹 rutis 不做的部分（provides 快照检查、workflowFiles 包处理）。  
   来源：dim-ref/docs/design/rutis-usage.md 附录 A.4
18. [fact/high] rutis 自 0.15.1 起事件是一条平总线（flat bus），0.16.0 保留该平总线并删除其兼容转接层。  
   来源：rutis/CHANGELOG.md:17-18 (rutis 4dc5cac1 2026-11-01)
19. [fact/high] 事件投递规则：每个监听者收到该名字的全部事件，不存储也不重放；emit 不等待，parallel 等待并汇总失败；同名事件按 emit 顺序启动监听者，跨名字无全序。事件 payload 必须是 serde，不得携带 handle、channel 或锁。保留前缀为 rutis/*（只听）和 internal/*（各运行时自用）。  
   来源：dim-ref/docs/design/rutis-usage.md §5；rutis/crates/rutis/README.md:41（一条平总线、五种分发模式）
20. [fact/high] Dim 明确拒绝再添加：plugin trait、作者可见的 scope 类型、resolver、manifest、role 字段、第二套服务目录、第二条总线，以及逐语言的 relay 或 adapter。  
   来源：dim-ref/docs/design/rutis-usage.md §1 末段；dim-ref/docs/adr/006-plugin-contract.md D2
21. [fact/high] ADR 006 的 Alternatives 表否决了：用 group 行上的 isolate 代替按实例 key 的服务；把 Session/branch 做成配置行；插件自己把 part 挂进实例；以及在 loader 的实例 group 中运行时注册模板。  
   来源：dim-ref/docs/adr/006-plugin-contract.md '## Alternatives considered' 表

## dim-approvals：dim permissions, approvals and questions

**问题**：Permission modes (read-only etc.), ADR 003 approval scope, crates/dim-agent-questions: how a question/approval is raised and answered by a client; trust for project-supplied plugins.

**摘要**：dim 的权限模型分两层：Permission 只裁决智能体（模型工具调用）的动作，由三个 preset（read-only / workspace-write / full-access）决定"能否运行、是否先询问"；配置驱动的命令（MCP 服务、Hook、workflow、插件包）不经过 Approval，按启用状态直接运行（ADR 003 D1/D2，Proposed）。项目来源的配置条目默认禁用，且项目文件无法自行启用，启用状态只存在用户本地配置里（D3）。ask_user 问题机制：模型调用工具后挂起等待，客户端通过 session.question.respond 回答或拒绝，答案作为该工具调用的 ToolResult 写入时间线，不产生额外事件；非交互会话直接返回错误结果不等待。CLI 以行模式提示回答，空行第一题即拒答。

## dim-tools：dim tool registry and MCP

**问题**：ToolRegistry: how a plugin declares a tool and its guide entry; per-branch tool adoption; session-scoped MCP servers; how Acard could provide tools (open a file at a line in a tab, read the current selection, show a diff) as a rutis service vs MCP.

## dim-workspace：dim workspace and file access model

**摘要**：dim 的工作区模型是“每个 Session 一个根”：SessionConfig.cwd 是单个字符串且创建后固定，文件事实里的 workspace 只认这个根的规范路径。仅当目标不在根内、也不属于系统根、owned 或 grant 时，才按需用 git rev-parse 识别同仓库的 linked worktree，并把可继承子树登记到 Session 内存中；不做全量 worktree list，也不永久缓存负结果。进程隔离的可写根只有 Session 工作区、已确认的 worktree 子树和 shell 输出目录，并在进程启动前确定，运行中的进程不扩边界。对 Acard 的多文件夹项目，dim 没有原生多根概念：非 Git 或不同仓库的文件夹不会自动获得访问，只能靠显式 grant、逐次审批，或为每个文件夹建独立 Session。
