## rutis-core：rutis: model and Go binding

**问题**：What rutis is (Cordis-style plugin runtime), plugin lifecycle, services, loader rows, sessions, rutis-bridge, cross-language calls, event bus; the Go binding in go/ and what a Go host can do.

**摘要**：rutis 是一个以 Cordis 生命周期模型为基础的插件运行时：Rust 核心（crates/rutis）只实现一次生命周期，依赖仅 tokio、tokio-util、thiserror、serde、serde_json；插件可用 TypeScript/JavaScript、Python、Go、Swift 编写，经 rutis-bridge 的 Session/Channel 跨进程、跨机器连接，经 rutis-loader 以声明式「行」（rows）管理。Go 绑定位于 go/rutis（模块 github.com/arcships/rutis/go/rutis，仅标准库，Go 1.24+），定位是插件侧：每个 Go 二进制即一个运行时进程，rutis.Serve 暴露插件，宿主（rutis-host 或 Rust 侧 GoResolver）按 manifest 路由调用。Go 程序目前没有公开的 loader/host API，只能作为被宿主拉起的插件端（ServeConn/ServeArgs），这一点是推断而非明文声明。对 Acard 而言，Go 原生应用若要用 rutis，应以子进程或 WebSocket 方式连接 rutis-host，而不是在 Go 进程内嵌入宿主。

1. [fact/high] rutis 自我定位为「A plugin runtime for software that iterates on itself」，Rust 核心，插件可用 TypeScript、Python、Go、Swift 编写，可跨进程和机器；生命周期模型来自 Cordis。  
   来源：~/Projects/rutis/README.md 顶部标题与第 27 行附近「The lifecycle model comes from Cordis」
2. [fact/high] 核心 crate 的依赖只有 tokio、tokio-util、thiserror、serde、serde_json（rutis-bridge 另加 erased-serde 与 rutis-macros）。  
   来源：~/Projects/rutis/crates/rutis/Cargo.toml [dependencies] 段（tokio、tokio-util、thiserror、serde、serde_json）；~/Projects/rutis/docs/design-philosophy.en.md §2 表格；~/Projects/rutis/crates/rutis-bridge/Cargo.toml:19-21
3. [fact/high] 插件是一个 trait Plugin：type Deps 声明依赖，async fn apply 在依赖就绪后注册服务、监听器和清理；通过 Ctx 注册的内容在插件停止时被撤回，依赖的服务被替换时插件会自动重启。  
   来源：~/Projects/rutis/crates/rutis/src/lib.rs:1-9（模块文档）与其中的 Printer 示例
4. [fact/high] Fiber 是生命周期容器，状态机有六个状态：Pending、Loading、Active、Failed、Unloading、Disposed，带依赖门控、级联卸载和清理恰好一次。  
   来源：~/Projects/rutis/crates/rutis/src/lib.rs 模块文档「Fiber: a six-state machine」；~/Projects/rutis/README.md 中 stateDiagram（Pending→Loading→Active/Failed→Unloading→Pending/Disposed）
5. [fact/high] 清理严格按 LIFO 串行执行，这是相对 Cordis（Cordis 为并发）的刻意加强。  
   来源：~/Projects/rutis/docs/core-features.en.md:82（Known deliberate strengthenings: cross-effect cleanup is strictly serial LIFO）
6. [fact/high] 事件总线是跨语言、跨进程、跨机器的单一逻辑总线，五种分发模式：emit、parallel、serial、waterfall、bail。  
   来源：~/Projects/rutis/docs/guide/plugin-api.en.md「The five modes」一节；~/Projects/rutis/README.md「How it works」段；~/Projects/rutis/crates/rutis/src/lib.rs 模块文档第 4 项

   来源：~/Projects/rutis/README.md「How it works」段（Services are registered by type in Rust and by name across languages）与「From experiment to production」段
8. [fact/high] rutis-bridge 提供 Channel（pipe::spawn、websocket::dial/listen、memory::pair）和 Session；远端插件以 <id>:<plugin> 形式挂入本地内核，服务双向可见，SessionHandle::run 让远端运行某插件，rutis-loader 对 <连接行>:<插件> 的行调用它。

**对 Acard 的含义**：rutis 的核心价值是把插件生命周期（依赖门控、替换后级联重启、LIFO 清理恰好一次）固化在 Rust 内核里，Acard 若要借用其插件模型，应当把它当作外部宿主进程或连接端，而不是 Go 库。Go 绑定是插件侧 SDK（每个二进制一个进程、按需启动、manifest 自描述），适合把 Acard 的阅读器扩展写成 Go 插件，但 Go 进程本身目前不能装载 rows；0.20 的 optional services 功能在本地分支上描述而尚未发布，设计 Acard 集成时要留意版本差异。

## rutis-compat：rutis version compatibility: attention vs dim
